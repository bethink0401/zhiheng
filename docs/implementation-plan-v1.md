## 2. 已确定且不得随意扩大的范围

### 2.1 已确定的产品决策

1. 产品暂定名为“知衡”。
2. 第一版只开发 iPhone App。
3. Apple Watch 只作为数据来源，第一版不开发独立 watchOS App。
4. 数据通过 iPhone 的 HealthKit 读取，而不是直接连接 Apple Watch。
5. 面向全社会成年用户，不只面向大学生。
6. 第一阶段是健康管理和生活方式改善产品，不是诊断或治疗软件。
7. 使用项目发起人的真实健康数据形成主要比赛故事，同时保留明确标注的模拟数据模式。
8. HealthGPT 是健康数据与 AI 对话方向的重点参考，但不直接换名称、换界面后参赛。
9. CareKit 是微计划、日程、完成记录和结果数据的重点基础框架，不只是可选参考。
10. 原创核心是个人基线、身体状态与主观感受对照、生活情境追问、微计划选择与效果分析和“我的有效方法”。
11. 每次开发后必须更新开发日志。

### 2.2 第一版必须完成的产品闭环

```text
读取 Apple Health 数据
        ↓
判断数据是否完整可靠
        ↓
展示最近状态和趋势
        ↓
用户记录精力、压力、身体感受和生活情境
        ↓
生成有数据依据、表达不确定性的洞察
        ↓
用户选择一个 3～7 天微计划
        ↓
记录执行并比较计划前后变化
        ↓
沉淀为“我的有效方法”
        ↓
AI 使用结构化健康事实回答用户问题
```

### 2.3 第一版明确不做

- iPad、Mac 和网页端。
- 独立 Apple Watch App。
- Yaoyao 跳绳计数整合。
- 医院挂号、实时号源和支付。
- 真人医生在线问诊。
- 疾病诊断、处方、用药剂量调整。
- 全量电子病历和完整 FHIR 系统。
- 社区、排行榜和好友竞争。
- 同时接入多个穿戴品牌。
- 复杂会员和商业化系统。
- 大型端侧语言模型。

这些功能可以进入未来路线图，但不能占用第一版闭环的开发时间。

## 3. 产品方案摘要

### 3.1 一句话定义

知衡是一款把 Apple Watch 长期数据、用户主观感受和生活情境放在一起分析，帮助用户理解身体变化并验证个人有效方法的 iPhone AI 健康助手。

### 3.2 用户面对的核心问题

Apple 健康已经能展示大量数据，但普通用户往往仍然不知道：

- 最近哪项变化最值得关注。
- 这次变化是不是持续趋势。
- 数据变化可能与哪些生活事件有关。
- 今天应该做一件什么小事。
- 做完以后是否真的对自己有帮助。

### 3.3 五项原创价值

#### 个人基线

主要比较用户当前状态和过去自己的差异，避免只用统一人群标准给用户打分。

#### 主客观对照

把睡眠、活动、静息心率等客观变化与精力、压力、身体感受放在同一页面。数据不能替代人的感受。

#### 生活情境

通过加班、旅行、饮酒、咖啡、生病、高强度运动等标签，补足穿戴数据无法解释的背景。

#### 微计划验证

一次只执行一个低风险、3～7 天的微计划，并比较计划前后的客观数据和主观体验。

#### 我的有效方法

持续积累“什么方法在什么情境下可能对我有效”，形成个人健康使用说明书。

### 3.4 五个主要页面

| 页面 | 首要任务 | 第一版核心内容 |
| --- | --- | --- |
| 今日 | 十秒内理解今天的状态 | 数据完整度、关键变化、主观签到、一个主要建议 |
| 洞察 | 理解变化依据 | 趋势图、基线对比、可能解释、生活事件、数据来源 |
| 微计划 | 把洞察转化为行动 | 当前计划、每日完成、计划结果、历史方法 |
| AI 助手 | 用对话理解数据 | 推荐问题、健康事实引用、追问、安全边界 |
| 我的 | 管理数据和设置 | 权限、数据源、通知、隐私、导出、演示模式 |

### 3.5 最重要的用户故事

比赛主演示优先采用下面的故事结构：

1. 用户打开 App，看到最近睡眠变短、静息心率偏离个人基线。
2. 系统没有直接说用户“压力过高”，而是指出数据事实并询问最近是否加班、运动增加或身体不适。
3. 用户标记“项目截止”和“下午喝咖啡”。
4. 系统给出一个“下午三点后不摄入咖啡因”的五天微计划。
5. 用户每日记录完成情况与精力感受。
6. 计划结束后，系统比较客观指标和主观感受。
7. 结果以“可能有效、样本仍少”的形式进入“我的有效方法”。
8. 用户向 AI 询问最近状态，AI 说明答案使用了哪些数据，不进行疾病诊断。

如果真实数据不支持咖啡故事，则从睡眠时间、活动、运动恢复或工作间歇中选择更符合数据的故事，不能为了演示伪造真实结论。

## 4. HealthGPT 的参考方式

### 4.1 为什么重点参考

HealthGPT 已经验证了一条很接近本项目的基础路径：

- 在 iOS 上读取 Apple Health 数据。
- 把健康数据转换为大模型可理解的内容。
- 让用户通过自然语言询问自己的健康数据。
- 支持文字、语音以及远程或本地模型的扩展思路。

这能帮助我们减少在基础架构上的试错，把时间投入知衡真正的差异化功能。

### 4.2 可以学习或依法复用的内容

后续研究 HealthGPT 时应形成一份功能映射，重点查看：

1. HealthKit 权限申请与数据读取流程。
2. 健康数据如何整理成 AI 上下文。
3. 对话界面如何管理加载、失败和重试状态。
4. 远程模型与本地模型如何抽象成统一接口。
5. 项目模块如何组织以及如何编写测试。
6. 数据发送到模型前进行了什么聚合。
7. 开源许可证、依赖许可证和署名要求。

在确实适合复用代码时，必须保留许可证和版权声明，并在项目中建立开源软件声明文件。

### 4.3 不能照搬的内容

- 产品名称、品牌、界面和完整交互流程。
- 将最近一段健康数据未经最小化处理直接发送给模型的方式。
- 只做“问数据、答数据”的单次聊天逻辑。
- 把 AI 自由推测当作趋势分析结果。
- 不符合知衡安全边界的医疗回答。

### 4.4 我们必须自己完成的部分

以下内容是参赛原创性的主要证据：

- 数据质量守门员。
- 个人基线算法。
- 趋势检测算法。
- 主客观状态矩阵。
- 生活事件关联和主动追问选择。
- 健康事实包。
- 微计划推荐与效果评估。
- “我的有效方法”可信度计算。
- 低焦虑语言和通知策略。
- 演示场景与评测数据集。

### 4.5 HealthGPT 参考验收物

完成参考研究不以“看过仓库”为准，而应产出：

- 一份功能和模块映射表。
- 一份可复用、仅参考、明确不用的三栏清单。
- 一次在本地运行的记录或无法运行的原因。
- 一份许可证与依赖说明。
- 至少三条相对于 HealthGPT 的原创差异说明。

### 4.6 CareKit 的重点使用方式

CareKit 不是 AI 分析框架，而是知衡“洞察之后如何采取行动”的基础框架。官方框架包含 CareKit、CareKitUI 与 CareKitStore。第一版重点使用 CareKitStore 的时间化、版本化计划模型，以及 CareKit 对任务执行进度的支持。

知衡与 CareKit 的映射如下：

| 知衡业务 | CareKit 模型 | 说明 |
| --- | --- | --- |
| 一次微计划 | `OCKCarePlan` | 组织一个三至七天的个人行动实验 |
| 每日行动 | `OCKTask` | 如下午三点后不喝咖啡、睡前呼吸 |
| 行动日期与目标 | `OCKSchedule` | 定义每天、指定时间或全天完成 |
| 某日执行记录 | `OCKOutcome` | 标识一次任务是否有执行结果 |
| 完成量与体验 | `OCKOutcomeValue` | 保存完成程度、困难度或简短量化反馈 |
| 完成率 | `CareTaskProgressStrategy`、`OCKAdherenceQuery` 或基于 Outcomes 的等价计算 | 作为计划评估和方法可信度的输入之一 |

具体原则：

1. CareKitStore 是微计划、任务、日程和完成结果的唯一事实来源。
2. SwiftData 不重复保存 CareKit 已经保存的任务完成状态。
3. SwiftData 继续保存主观签到、生活事件、洞察、分析快照和“我的有效方法”。
4. 两个存储通过稳定的字符串 ID 关联，例如 `carePlanID`、`taskID` 和 `insightID`。
5. 个人基线、趋势和计划效果由知衡算法计算；CareKit 负责可靠记录，不负责判断方法是否有效。
6. CareKitUI 以小型验证结果决定使用范围。若 UIKit 组件不符合知衡的 SwiftUI 视觉和交互，可重点使用 CareKitStore，并用自定义 SwiftUI 页面展示。
7. 第一版不引入 CareKitFHIR，也不把普通生活方式计划包装成疾病治疗方案。

CareKit 研究必须产出：

- OCKCatalog 与 OCKSample 的运行记录。
- Care Plan、Task、Schedule、Outcome 和 Outcome Value 的映射验证。
- 一条三天微计划的最小技术样例。
- CareKitUI 直接使用与 SwiftUI 自定义展示的对比结论。
- CareKit BSD 许可证和署名记录。

## 5. 第一版技术方案

### 5.1 技术选型

| 层级 | 默认选择 | 原因 |
| --- | --- | --- |
| App 界面 | SwiftUI | 苹果原生、适合 iPhone、便于快速迭代 |
| 健康数据 | HealthKit | Apple Watch 数据在 iPhone 上的标准来源 |
| 行动计划 | CareKit、CareKitStore | 管理计划、任务、日程、完成记录与结果值 |
| 其他本地存储 | SwiftData | 保存主观记录、标签、洞察、评估摘要和方法 |
| 图表 | Swift Charts | 原生、风格与 iOS 一致 |
| 通知 | UserNotifications | 完成计划和低频洞察提醒 |
| AI 网络层 | 可替换的 `AIService` 接口 | 模型供应商变化时不用重写产品逻辑 |
| 本地分析 | 纯 Swift 算法模块 | 保证趋势可测试、可解释、离线可用 |
| 报告 | SwiftUI 渲染或 PDFKit | 后期生成可分享健康摘要 |
| 测试 | XCTest / Swift Testing | 验证算法、数据边界和关键流程 |

### 5.2 对 Spezi 的决策

已在 S02 完成 HealthGPT 和 SpeziHealthKit 的源码、依赖与第一版需求对比。知衡第一版使用苹果原生 HealthKit 作为唯一健康数据访问层，不引入 Spezi/SpeziHealthKit 依赖。

- 第一版主要是按需读取最近 28～90 天数据并进行确定性聚合，原生 HealthKit 足以覆盖。
- SpeziHealthKit 会带来 Spezi、存储与异步算法等传递依赖，当前收益不足以抵消升级和调试成本。
- 参考其权限、样本删除、睡眠处理和测试设计，不复制框架职责。
- 若未来产生可靠后台增量同步等明确需求，必须创建新的独立技术验证任务后才能改变选择。

证据和固定版本见 `docs/open-source-reference-analysis.md`。

### 5.5 核心数据模型

#### 客观健康数据

统一为应用自己的领域模型，避免页面直接依赖 HealthKit 类型：

```text
HealthMetricSample
- id
- metricType
- startDate
- endDate
- value
- unit
- sourceName
- deviceName（可选）
```

第一版指标：

- 步数。
- 睡眠时长。
- 入睡与起床时间。
- 静息心率。
- HRV。
- 活动能量。
- 运动分钟。

优先保证步数、睡眠、静息心率和 HRV 四类数据完整跑通；活动能量和运动分钟可以在同一阶段后半部分补齐。

#### 每日主观记录

```text
DailyCheckIn
- date
- energyLevel：1...5
- stressLevel：1...5
- bodyFeeling：1...5
- symptoms：可选短文本
- note：可选短文本
- createdAt
```

#### 生活事件

```text
ContextEvent
- id
- type
- startDate
- endDate（可选）
- intensity（可选）
- note（可选）
```

默认类型包括加班、考试或截止日期、旅行、夜班、咖啡、饮酒、生病、高强度运动、午睡、照护家人、未佩戴设备和自定义。

#### 微计划

微计划的执行部分不再另建一套重复模型，而是重点使用 CareKit：

```text
OCKCarePlan
└── OCKTask
    └── OCKSchedule：生成每日任务 occurrence
        └── OCKOutcome
            └── OCKOutcomeValue：完成量、困难度或反馈
```

知衡另外保存一个轻量 `PlanAnalysisMetadata`，只保存 CareKit 不负责的分析信息：

```text
PlanAnalysisMetadata
- carePlanID
- createdFromInsightID（可选）
- primaryGoal
- baselineSnapshot
- relatedMetricTypes
- evaluationStatus
- interferenceEventIDs
```

`PlanAnalysisMetadata` 不能再保存一份任务是否完成，以 CareKit Outcome 为准。

#### 我的有效方法

```text
EffectiveMethod
- id
- sourcePlanTemplateID
- title
- applicableContext
- runCount
- completionRate
- objectiveChanges
- subjectiveChanges
- dataCoverage
- confidenceLevel
- lastRunDate
- conclusion
```

### 5.6 本地优先和数据最小化

- 原始 HealthKit 样本默认只在设备本地处理。
- 本地保存的主观记录不默认上传。
- AI 只接收经过聚合的健康事实包，不接收完整原始样本列表。
- 每次 AI 回答应能展示使用了哪些指标和时间范围。
- 开发阶段密钥放在不提交版本管理的配置中。
- 正式测试或发布时通过服务端代理调用模型，客户端不内置正式密钥。
- 日志和崩溃信息不得包含真实健康数据、对话原文或身份信息。

## 6. 数据分析规则

### 6.1 数据质量守门员

任何趋势和 AI 解释之前先判断数据是否足够。

每项指标至少计算：

- 请求时间范围内有数据的天数。
- 数据覆盖率。
- 最近一次数据时间。
- 数据来源。
- 是否存在明显断档。
- 是否可能因为设备未佩戴而缺失。

默认规则：

- 最近 7 天至少有 4 个有效日，才能形成短期趋势。
- 28 天基线至少有 14 个有效日，才能称为个人基线。
- 不满足门槛时显示“数据不足”，不能输出明显上升或下降。
- 对睡眠和 HRV 等设备依赖较强的数据，缺失不能按 0 处理。
- 数据源发生变化时进行标记，避免把换设备造成的差异当作生理变化。

具体门槛应通过真实数据测试后调整，并在日志记录调整原因。

### 6.2 个人基线

默认采用最近 28 个日历日作为基线窗口，窗口内至少 14 个有效日才形成个人基线；最近 7 个日历日作为当前窗口。

优先使用中位数而不是平均数，降低极端值影响。每个结果必须同时保留：

- 基线值。
- 当前值。
- 绝对变化。
- 相对变化百分比。
- 有效样本天数。
- 数据覆盖率。
- 计算时间范围。

第一版不生成一个综合“健康分”。各指标分别解释，更符合可解释和低焦虑原则。

### 6.3 趋势检测

第一版只输出三档：

- 未见明确变化。
- 值得继续观察。
- 存在持续变化。

趋势成立至少需要同时满足：

1. 数据质量达到门槛。
2. 当前窗口相对基线超过该指标的最小变化阈值。
3. 变化不是只由单日异常值造成。
4. 最近数日具有一定一致性。

算法可以使用中位数、四分位距或 MAD 等稳健统计方式。阈值在编码时集中配置，不散落在页面代码中。

### 6.4 身体状态与主观感受对照

程序先根据客观趋势形成“稳定、偏离、数据不足”，再与主观记录组合：

| 客观状态 | 主观状态 | 输出原则 |
| --- | --- | --- |
| 稳定 | 较好 | 肯定状态，减少打扰 |
| 偏离 | 较差 | 建议一个低风险行动或降低负荷 |
| 偏离 | 较好 | 说明数据变化但尊重感受，继续观察 |
| 稳定 | 较差 | 尊重用户感受，询问症状或生活背景 |
| 数据不足 | 任意 | 明确数据不足，不能强行判断 |

这里的输出首先由规则生成，AI 只负责把规则结果表达得自然清楚。

### 6.5 微计划效果评估

计划评估至少需要：

- 计划前基线窗口。
- 计划执行窗口。
- 计划完成率。
- 目标相关的客观指标。
- 同期主观感受。
- 数据覆盖率。
- 可能影响结果的生活事件。

第一版结论只使用：

- 可能有帮助。
- 暂未观察到明显变化。
- 执行不足，无法判断。
- 数据不足，建议继续观察。
- 主观感受改善但客观指标未见明显变化。
- 客观指标改善但主观感受未同步改善。

不得使用“证明有效”“一定改善”“治疗了”等因果或医疗表达。

### 6.6 方法可信度

“我的有效方法”不能只因一次结果自动标记为高可信。可信度至少考虑：

- 执行次数。
- 每次完成率。
- 数据覆盖率。
- 客观变化方向是否一致。
- 主观变化方向是否一致。
- 是否存在明显干扰事件。

建议显示为：

- 初步观察：完成 1 次且数据可用。
- 可能适合：至少完成 2 次，结果方向基本一致。
- 较稳定方法：至少完成 3 次，完成率和数据质量良好，结果较一致。
- 结果不明确：样本、执行或数据不足。

比赛第一版只需完整跑通“初步观察”，但模型和页面应为多次执行预留空间。

## 7. AI 方案与安全边界

### 7.1 AI 在产品中的职责

AI 可以：

- 用自然语言总结程序已经计算出的事实。
- 解释指标的常识性含义。
- 指出多个可能影响因素。
- 在缺少背景时提出一个关键追问。
- 从安全的模板库中推荐一个微计划。
- 回答“最近睡眠怎么样”一类个人数据问题。
- 帮用户整理就医沟通要点。

AI 不可以：

- 自己从原始数据随意计算医学结论。
- 给出确定疾病诊断。
- 推荐处方药或调整剂量。
- 把相关性描述为因果。
- 因单次异常制造紧急感。
- 隐藏数据不足和模型不确定性。

### 7.2 健康事实包

AI 不直接读取整个 HealthKit 数据库。程序生成结构化事实包，例如：

```json
{
  "period": {
    "current": "最近7个有效日",
    "baseline": "此前28个有效日"
  },
  "data_quality": {
    "sleep_coverage": 0.86,
    "heart_rate_coverage": 1.0,
    "wear_gap_detected": false
  },
  "facts": [
    {
      "metric": "sleep_duration",
      "current": 6.35,
      "baseline": 7.08,
      "unit": "hour",
      "direction": "down",
      "confidence": "medium"
    }
  ],
  "subjective": {
    "energy": 2,
    "stress": 4,
    "body_feeling": 2
  },
  "context_events": ["deadline", "afternoon_caffeine"],
  "allowed_plan_templates": ["caffeine_cutoff", "earlier_bedtime"]
}
```

事实包中的数值必须来源于本地算法，AI 不得擅自补充不存在的数据。

### 7.3 AI 结构化输出

模型应返回可以校验的结构，而不是任意长文本：

```text
- summary：一句总结
- observedFacts：引用哪些事实
- possibleFactors：可能因素，明确不是确定原因
- uncertainty：数据不足或其他可能性
- followUpQuestion：最多一个问题
- suggestedAction：只能来自允许的低风险模板
- safetyLevel：normal / caution / urgent
- escalationMessage：必要时的专业帮助提示
```

客户端校验失败时，不直接展示原始模型结果，而应降级成规则生成的本地摘要。

### 7.4 症状对话边界

第一版可以允许用户描述症状，但只提供：

- 一般健康信息。
- 建议记录症状持续时间和伴随情况。
- 提醒何时考虑咨询医生。
- 对明显紧急信号建议立即寻求急救或当地紧急服务。

第一版不宣传“智能诊断”或“AI 医生”。急症规则应独立于语言模型，至少覆盖胸痛、严重呼吸困难、意识异常、严重出血、疑似卒中表现和自伤风险等场景。具体文案在发布前应请医学专业人士审阅。

### 7.5 AI 失败降级

- 无网络：仍展示本地趋势、洞察模板和计划。
- 模型超时：提供重试，不丢失用户输入。
- 输出格式错误：使用本地规则摘要。
- 模型拒绝：解释边界并提供安全替代信息。
- 事实包为空：明确说明数据不足，不发起无意义请求。

## 10. 设计与体验要求

### 10.1 视觉原则

- 整体接近 iOS 原生健康产品的安静、可信和清晰感。
- 颜色主要用于区分信息，不用大面积红色制造紧急感。
- 不使用“健康总分”作为首页核心。
- 图表必须标明单位、时间范围和缺失数据。
- 主观感受与客观数据使用平等的视觉权重。
- AI 回答中的事实依据可展开查看。

### 10.2 文案规则

优先使用：

- “相较于你的近期基线”。
- “最近几天出现了持续变化”。
- “可能与……有关，也可能存在其他因素”。
- “当前数据不足以判断”。
- “如果同时出现明显不适或症状持续，请咨询专业人士”。

避免使用：

- “你不健康”。
- “你的压力很危险”。
- “AI 判断你患有……”。
- “这个方法已经证明有效”。
- “只要这样做就会改善”。

### 10.3 通知预算

- 默认每天最多一条非紧急提醒。
- 没有明确价值时不通知。
- 同一趋势不重复提醒。
- 用户主动执行计划时，计划提醒优先于一般洞察。
- 紧急医学信息不依赖后台推送检测，本产品也不承诺持续医疗监护。

## 11. 测试矩阵

### 11.1 数据场景

- 完整 90 天数据。
- 只有 7 天数据。
- 中间连续缺失 5 天。
- 最近两天未佩戴。
- 换 Apple Watch 或数据源。
- 一天有多个来源重复记录。
- 时区变化和跨午夜睡眠。
- 夏令时变化。
- 极端异常值。
- 用户撤销某项权限。

### 11.2 算法场景

- 稳定无变化。
- 单日异常但整体稳定。
- 缓慢持续变化。
- 最近窗口与基线明显不同。
- 数据不足。
- 客观改善、主观变差。
- 客观变差、主观良好。
- 计划完成率高但无变化。
- 计划完成率低无法判断。
- 多个干扰事件重叠。

### 11.3 AI 场景

- 询问最近睡眠。
- 询问近期运动变化。
- 询问“为什么最近很累”。
- 数据不足时要求确定答案。
- 要求诊断疾病。
- 要求调整药物。
- 描述明显紧急症状。
- 要求模型忽略安全规则。
- 模型返回错误 JSON。
- 网络超时和断网。
- 用户输入极长文本。
- 对话中出现与事实包矛盾的陈述。

### 11.4 用户体验场景

- 第一次使用且没有权限。
- 只授权步数。
- 没有 Apple Watch。
- 字体设为最大。
- 使用 VoiceOver。
- 深色模式。
- 用户不想每日签到。
- 用户删除计划和主观记录。
- 用户不理解 HRV。
- 用户因指标变化感到焦虑。

## 13. 风险控制

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 范围失控 | 开始讨论医院、Watch App、多端 | 回到 S00 范围，所有新增项进入未来清单 |
| HealthKit 数据不足 | 睡眠或 HRV 有效日太少 | 使用步数/睡眠故事或明确模拟场景 |
| HealthGPT 依赖过重 | 无法解释项目自己的架构 | 只保留经过验证的模块，自研核心算法 |
| CareKit 与 SwiftUI 集成复杂 | UIKit 页面影响开发和视觉统一 | 核心使用 CareKitStore，UI 经适配层使用自定义 SwiftUI |
| CareKit 与 SwiftData 重复存储 | 完成状态不一致 | CareKitStore 独占计划执行事实，SwiftData 只存分析和其他记录 |
| AI 编造 | 回答出现事实包外的具体数据 | 结构化输出、客户端校验和本地降级 |
| 医疗误导 | 使用诊断或确定因果语言 | 安全规则、固定测试集、专业审阅 |
| 真实数据演示不稳定 | 最近一周没有明显变化 | 预录真实故事，现场使用演示模式兜底 |
| 健康焦虑 | 用户误以为分数代表疾病 | 不做总分，显示依据和不确定性 |
| 密钥泄露 | 配置出现在工程或日志 | 本地忽略文件、扫描、后端代理 |
| 学业时间冲突 | 连续多周没有进展 | 优先完成最小闭环，暂停 P1/P2 |
| 开源合规风险 | 复制代码但没有记录来源 | 开源声明、提交记录和许可证检查 |

## 14. 开发日志制度

每日开发日志位于[`开发日志/`](../开发日志/README.md)。它是强制项目资产，不是开发完成后的可选总结。`docs/development-log.md` 作为制度建立前的历史归档保留。

### 14.1 什么时候必须记录

- 完成一个任务编号时。
- 某项任务被阻塞时。
- 修改产品范围或技术方案时。
- 引入、升级或移除依赖时。
- 修改算法阈值时。
- 接入或更换 AI 模型时。
- 发现隐私、安全或医疗风险时。
- 完成真机、用户或比赛测试时。
- 修复会影响演示的错误时。

### 14.2 每条日志必须包含

- 日期和任务编号。
- 本次目标。
- 实际完成内容。
- 修改文件。
- 验证方式和结果。
- 关键决定及原因。
- 已知问题或风险。
- 下一项具体任务。

### 14.3 日志与任务状态的关系

1. 开始工作时可以把任务标为 `[~]`。
2. 代码或文档完成但未验证时仍为 `[~]`。
3. 验证通过并写日志后才能标为 `[x]`。
4. 无法继续时标为 `[!]`，日志必须记录阻塞证据和可行替代路线。
5. 每个工作日使用 `开发日志/YYYY-MM-DD.md`；同一天按工作发生顺序追加，旧事实不删除；如果结论后来改变，新增一条更正记录。

### 14.4 后续开发的固定收尾检查

每次结束工作前依次确认：

- [ ] 需求是否在当前范围内。
- [ ] 修改是否只影响预期文件。
- [ ] 是否完成了必要测试或人工验证。
- [ ] 是否更新任务状态。
- [ ] 是否追加开发日志。
- [ ] 是否写明下一项任务。
- [ ] 是否没有把密钥和真实健康数据写入仓库。
