## 1. 执行原则

项目采用“小步推进、完成验证、立即记录”的方式，不一口气开发多个大模块。

默认每次开发批次：

- 只设一个主要目标。
- 对应一个任务编号或一个不可拆分的小任务组。
- 优先修改 1～3 个职责相关文件；确需更多文件时先说明原因。
- 先完成最小可验证结果，不顺手扩展 P1/P2 功能。
- 测试通过并更新当天日志后才开始下一项。

如果一个任务预计无法在一次清晰的开发回合中完成，先拆成“接口/模型、实现、测试、界面接入”等子任务。

## 2. 每次开发的固定流程

### 开始前

1. 阅读 `AGENTS.md`。
2. 阅读 `开发日志/` 中最新日志。
3. 确认当前任务编号和需求编号。
4. 检查已有文件和未提交修改，避免覆盖用户工作。
5. 在当天日志写入今日目标；文件不存在时创建。
6. 必要时把实施清单中的任务标为 `[~]`。

### 实施中

1. 只完成当前任务所需的最小改动。
2. 遇到范围扩大、安全风险或架构冲突时暂停扩展。
3. 优先查官方文档并用最小技术样例验证不确定 API。
4. 不在终端和日志中输出密钥或真实健康数据。
5. 每完成一个独立结果立即追加当天日志，不等到一天结束后凭记忆补写。

### 完成前

1. 执行与风险匹配的测试或人工检查。
2. 记录成功和失败结果。
3. 更新任务状态；只有验证通过才标 `[x]`。
4. 更新当天日志的完成事项、待办、风险和唯一下一步。
5. 检查没有范围外功能、重复数据层、敏感信息或无许可证代码。
6. 向用户汇报结果和下一项小任务。

## 3. 阶段门禁

后一个阶段只有在前一个阶段达到退出条件后才能正式开始。用户明确要求插入新任务时，也要保持已有安全和隐私门禁。

### G0 项目治理完成

对应 S00。

必须具备：

- 产品需求基线。
- 技术设计规范。
- 执行步骤。
- 质量与安全标准。
- `AGENTS.md`。
- 每日开发日志目录。

退出条件：文件存在、链接有效、当前下一步一致。

### G1 开发条件确认

对应 S01。

按以下小任务依次进行：

1. S01-01：读取 Mac、macOS、Xcode 和磁盘信息。
2. S01-02：确认测试 iPhone 型号与 iOS。
3. S01-03：确认 Apple Watch 和佩戴情况。
4. S01-04：列出 Apple Health 最近 90 天可用数据类型。
5. S01-05：统计四项核心数据有效天数。
6. S01-06：确认 Apple ID、开发签名和真机安装条件。
7. S01-07：记录比赛、截止日期和评分规则。
8. S01-08：确定真实数据展示和脱敏规则。

每个任务单独记录。设备信息可以只读检查；涉及打开系统界面或用户账号操作时先说明。

退出条件：形成一份设备、账号、数据和比赛条件清单，知道最早截止日期和真机 HealthKit 是否可行。

### G2 开源参考与技术样例

对应 S02。

按两个独立方向推进，不同时大规模改造：

#### HealthGPT 路线

1. 固定仓库版本和许可证。
2. 尝试运行原项目。
3. 画出 HealthKit 到 AI 的数据流。
4. 建立复用、参考、不采用清单。
5. 查阅原生 HealthKit 与 SpeziHealthKit 对比记录。
6. 使用已确定的苹果原生 HealthKit 数据层。

#### CareKit 路线

1. 运行 OCKCatalog。
2. 运行 OCKSample。
3. 创建一个独立三天计划样例。
4. 验证 `OCKSchedule`。
5. 写入和读取 `OCKOutcome`。
6. 使用当前 CareKit 进度 API 或 Outcomes 等价计算完成率。
7. 验证暂停、结束和历史版本。
8. 比较 CareKitUI 与自定义 SwiftUI。

退出条件：两条路线都有运行或明确失败记录；CareKitStore 最小计划闭环可用；HealthKit 数据层有证据化选择。

### G3 工程骨架

对应 S03。

拆分为：

1. 创建最小 SwiftUI 工程并能运行。
2. 添加五个空导航页。
3. 建立 Domain/Data/Analytics/AI 目录和协议。
4. 添加测试 Target 并运行一个示例测试。
5. 引入固定版本 CareKit。
6. 建立 `CareKitPlanStore` 最小读写。
7. 配置 HealthKit Capability 和非敏感占位说明。
8. 建立密钥忽略与配置机制。

退出条件：模拟器和真机至少一种可以稳定运行；测试可执行；CareKitStore 能读写；没有密钥。

### G4 健康数据可见

对应 S04～S06。

一次只接入一种指标：

1. 步数。
2. 睡眠。
3. 静息心率。
4. HRV。

每种指标都按“授权→查询→领域模型→无数据→测试→页面”完成后再开始下一种。之后实现 Demo Provider、数据质量和基础图表。

退出条件：真机读取四类数据；演示数据可替换；图表和缺失状态正确。

### G5 本地洞察可用

对应 S07～S09。

顺序：

1. 数据质量报告。
2. 28 天基线。
3. 7 天当前窗口。
4. 一种指标趋势及测试。
5. 扩展到四类核心指标。
6. 主观签到。
7. 生活事件。
8. 主客观对照。
9. 可解释洞察卡。

退出条件：完全关闭 AI 时仍可生成一条有数据依据的洞察。

### G6 CareKit 行动闭环

对应 S10～S11。

先只完成一个计划模板，推荐“下午咖啡截止”或更符合真实数据的模板：

1. 模板转换为 `OCKCarePlan`、`OCKTask`、`OCKSchedule`。
2. 开始计划。
3. 每日写入 Outcome。
4. 展示完成率。
5. 保存计划前基线。
6. 计划结束评估。
7. 生成一张“初步观察”方法卡。
8. 流程稳定后才增加其他模板。

退出条件：一个计划使用真实 CareKitStore 完整跑通，不是写死的演示页面。

### G7 AI、安全和通知

对应 S12～S14。

顺序：

1. 事实包构建和快照测试。
2. 本地假 AIService 验证界面。
3. 结构化响应校验。
4. 安全预检查和后检查。
5. 接入单一开发模型服务。
6. 断网与超时降级。
7. 低频通知。
8. 隐私、可访问性和开源合规检查。

退出条件：模型无法绕过事实包和安全规则；断网不影响本地核心流程。

### G8 真实验证与产品交付

当前按起点审计顺序执行 S09；S15 的真实验证和产品稳定性工作在核心闭环补齐后继续。S16 比赛申报、PPT、路演和比赛视频暂停。

顺序：

1. 选择脱敏真实故事。
2. 连续记录主观感受。
3. 完成一个真实微计划。
4. 进行 5～10 人首轮测试。
5. 修复影响理解、隐私和稳定性的高优先问题。
6. 完成可安装、可运行、可恢复的产品版本与用户说明。

退出条件：真实与模拟数据标记清楚，断网降级可用，核心产品闭环稳定，隐私和安全边界可说明。

## 5. 阻塞处理

任务遇到问题时：

1. 先做安全的只读诊断。
2. 查官方文档和当前固定版本。
3. 尝试一个最小替代方案。
4. 不连续扩大修改范围。
5. 标记 `[!]` 并在当天日志记录证据、影响和可选方案。
6. 只有需要用户选择、授权或外部状态改变时才停下询问。

不能因为工作困难、尚未完成或需要更多时间就标记完成或隐藏问题。

## 6. 范围控制

以下情况视为范围扩大，必须先记录并获得用户明确方向：

- 从 iPhone 扩展到其他平台。
- 添加诊断、用药或医院服务。
- 接入新的穿戴品牌。
- 更换 CareKit 核心计划方案。
- 上传原始健康数据。
- 引入新后端或账号体系。
- 新增付费、广告或社区功能。

小型重构、测试、错误状态和隐私保护属于正常实现步骤，无需额外扩大产品范围。
