# 知衡 HealthKit 扩展数据目录与分级授权方案

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 更新日期 | 2026-08-21 |
| 对应任务 | S04-12 |
| 当前状态 | 方案完成；尚未扩大真实权限 |
| 适用平台 | iPhone 第一版及后续迭代 |

## 1. 结论

知衡可以逐步覆盖 Apple Health 中绝大多数与产品目标相关、当前设备支持且用户愿意授权的数据，但“全部接入”不应实现成首次启动时一次性申请全部 HealthKit 类型。

原因不是技术偷懒，而是产品正确性：

- HealthKit 按数据类型进行细粒度授权，Apple 明确建议在真正需要某类数据时再请求，而不是必须一次申请全部类型。
- Apple 不向 App 公开用户是否拒绝了某一项读取权限；没有返回样本也可能是没有记录或只授权了有限历史。
- HealthKit 不只有普通数值，还包括睡眠区间、活动汇总、训练、心电图、听力、用药、症状、临床记录和路线等不同模型，不能用同一套查询和图表粗暴处理。
- 临床记录需要额外 Capability、单独权限页和有效隐私政策，Apple 也提醒无真实用途时可能无法通过审核。
- 用药、生殖健康、症状、心律事件、血糖和临床记录等数据敏感度高，若没有对应功能、解释规则和安全测试，申请权限本身就会损害信任。

Apple 官方依据：

- [HealthKit 数据类型总览](https://developer.apple.com/documentation/healthkit/data-types)
- [HealthKit 授权与有限历史访问](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)
- [HealthKit 工程配置与临床记录限制](https://developer.apple.com/documentation/healthkit/setting-up-healthkit)
- [临床健康记录访问要求](https://developer.apple.com/documentation/healthkit/accessing-health-records)

## 2. 产品中的“全部数据”如何呈现

随着数据类型从 6 类扩展到几十类，今日页不能无限堆卡片。采用三层信息架构：

```text
今日
├── 用户置顶的核心卡片（默认 6 类，可调整）
├── 今日活动总览
└── 数据状态与权限入口（页面底部）

全部健康数据
├── 活动与训练
├── 心肺与恢复
├── 睡眠与正念
├── 身体测量与行动能力
├── 环境、听力与习惯
└── 用户明确启用的敏感数据组

洞察
├── 7/28 天趋势
├── 个人基线
├── 主客观对照
└── 可解释分析与后续 AI 事实依据
```

默认今日页只显示最常用、可解释的卡片。用户可以在“全部健康数据”中搜索、查看和置顶，不应把一百多个数据类型全塞进首页。

## 3. 数据分级目录

### L0：当前已经接入

| 数据 | 当前用途 | 状态 |
| --- | --- | --- |
| 步数 | 今日活动、7/28 天趋势、90 天覆盖 | 已完成；Watch 优先、iPhone 兜底 |
| 活动能量 | 今日活动与运动负荷背景 | 已完成 |
| Apple 运动分钟 | 今日活动与运动负荷背景 | 已完成 |
| 睡眠分析 | 昨夜睡眠、覆盖和趋势 | 已完成 |
| 静息心率 | 最近记录、覆盖和趋势 | 已完成 |
| HRV（SDNN） | 最近记录、覆盖和趋势，不直接等同压力 | 已完成 |

### L1：下一批高价值、低到中等敏感数据

这一层与知衡的“看趋势→理解状态”直接相关，适合在核心闭环稳定后优先实现。

| 数据组 | 建议类型 | 用户价值 | 主要限制 |
| --- | --- | --- | --- |
| 训练摘要 | `HKWorkout`、训练类型、时长、能量、距离 | 看运动结构、恢复与负荷变化 | 训练路线涉及精确位置，第一批不读取 |
| 日常活动 | 步行/跑步距离、骑行距离、楼层、站立时间、基础能量 | 比步数更完整地解释活动变化 | 累计数据需使用 HealthKit 统计查询防重复 |
| 常规心肺 | 心率、步行平均心率、运动后一分钟心率恢复、VO₂ max | 形成个人心肺和恢复趋势 | 数据频率、设备支持与训练场景不同 |
| 睡眠恢复 | 呼吸频率、睡眠手腕温度 | 与睡眠和主观感受对照 | 手腕温度与部分睡眠数据依赖支持设备和佩戴条件 |
| 正念与环境 | 正念时段、日照时间 | 补充压力与生活情境 | 不能把单项记录写成情绪或疾病因果 |
| 身体测量 | 体重、身高、BMI、体脂、瘦体重、腰围 | 观察长期变化并辅助目标管理 | 多数依赖用户手动记录或第三方秤 |
| 行动能力 | 步行速度、步长、双支撑、步态不对称、步行稳定性、上下楼速度 | 覆盖中老年人、康复和行动变化 | 数据可能稀疏；步行稳定性有特定携带和计算条件 |

Apple 说明步行稳定性由系统在满足设备、携带位置和数据量条件时生成，可能约数天才有一个样本，因此不能按每日数据要求它。[Apple Walking Steadiness](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/applewalkingsteadiness)

### L2：用户按场景主动启用的数据

这些数据有价值，但不是每个人都有，也不适合在首次授权时统一申请。

| 数据组 | 示例 | 启用条件 |
| --- | --- | --- |
| 血压与血糖 | 收缩压、舒张压、血糖 | 用户主动进入对应模块；先建立单位、来源、异常输入和医疗边界测试 |
| 血氧与体温 | 血氧饱和度、体温 | 设备与地区支持检查；避免宣称持续监护或诊断 |
| 听力与噪声 | 环境噪声、耳机音量、暴露事件、听力图 | 用户主动启用听力健康页面 |
| 饮食与饮水 | 能量、宏量营养素、水、咖啡因 | 用户需要饮食或咖啡因对照；不默认申请全部营养微量元素 |
| 饮酒 | 酒精饮品数量等 | 用户主动选择，通知默认不显示敏感细节 |
| 症状记录 | 头痛、恶心、气短等 HealthKit 症状类型 | 症状整理模块完成并通过紧急症状安全测试后 |
| 心律相关 | 高/低心率事件、不规则心律事件、房颤负荷、心电图 | 独立高敏感说明、设备支持检查和医学文案审阅后 |
| 生殖与周期 | 经期、排卵、怀孕、哺乳、避孕等 | 独立功能、独立用途说明、明确删除与隐藏能力后 |
| 心理与主观状态 | 正念、State of Mind 等系统记录 | 与知衡主观签到职责对齐后，避免重复和越界推断 |

Apple 的症状类型覆盖多类医学症状，不能把它们当普通标签使用；具体类型见[症状类型目录](https://developer.apple.com/documentation/healthkit/symptom-type-identifiers)。营养数据也无需全量接入，Apple 建议按产品关注点选择必要项目，见[营养类型目录](https://developer.apple.com/documentation/healthkit/nutrition-type-identifiers)。

### L3：第一版不接入

| 数据 | 暂不接入原因 | 重新评估条件 |
| --- | --- | --- |
| 临床健康记录/FHIR | 需要额外 Capability、单独授权、隐私政策和明确临床用途；超出当前 MVP | 有真实医院数据场景、隐私政策、医学与合规审阅 |
| 用药与剂量事件 | iOS 26 提供专门对象、查询和逐药授权；涉及用药依从性与高风险解释 | 建立独立用药模块，明确不提供停药或剂量调整，并完成医学安全测试 |
| 训练路线 | 包含精确位置，不是当前趋势闭环必需 | 用户明确需要路线分析且位置隐私方案通过 |
| 原始心电波形/心跳序列 | 数据量大、解释风险高，当前没有必要的专业分析能力 | 明确的非诊断用途、设备验证和医学专业审阅 |
| 胰岛素、肺功能等疾病管理数据 | 容易进入疾病管理与治疗建议边界 | 独立疾病管理产品范围、专业审核和合规评估 |

HealthKit 在 iOS 26 新增用药与剂量事件访问，并采用特定的用药对象和授权流程；这不是普通数值类型扩展，需单独设计。[WWDC25：HealthKit Medications API](https://developer.apple.com/videos/play/wwdc2025/321/)

## 4. 分级授权流程

### 首次连接

当前统一连接入口请求应用已经实现的十六类普通只读数据：原有十一类指标，加上 2026-08-30 完成的步行与跑步距离、爬楼层数、步行速度、步长和心肺适能。原六类仍作为最小核心集合用于连接状态和基础验收；新增类型无样本、设备不支持或用户未授权时保持缺失，不影响其他指标使用。高敏感数据、临床记录、用药、路线和原始心电仍不进入统一连接入口。

### 用户主动启用新模块

每个数据组采用以下流程：

1. 用户进入功能页或“全部健康数据”。
2. 页面解释要读取什么、为什么、是否上传、缺失会怎样处理。
3. 用户点击“连接这一组数据”。
4. 仅请求该组对应的只读类型。
5. 请求完成后查询可见数据，但不声称每项都已授权。
6. 无数据时区分设备不支持、历史不足、当前不可见和查询失败能区分的部分；不能把无样本写成 0。
7. 用户可以在“我的→数据与隐私”看到已启用功能组、重新打开系统健康权限页和取消知衡内展示。

Apple 允许用户只授权最近一段历史，后续查询需要尊重最早授权日期；知衡不能默认自己拥有完整历史。[授权与有限历史访问](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)

## 5. 技术实现标准

当前十六类指标继续由领域枚举统一隔离；后续出现更多查询策略或分组授权入口时，再演进为“指标注册表”，页面仍不得直接操作 HealthKit 类型。

建议模型：

```text
HealthMetricDescriptor
- stableID
- title
- category
- sensitivityLevel
- minimumOSVersion
- deviceRequirements
- domainUnit
- queryStrategy
- aggregationStrategy
- sourcePolicy
- detailPresentation
- trendEligibility
- permissionGroup
```

查询策略至少分为：

- 累计数值：优先 `HKStatisticsQuery` / `HKStatisticsCollectionQuery`，由 HealthKit 合并多来源。
- 离散数值：最近值、中位数或日均值，必须按指标单独定义。
- 类别区间：睡眠、正念等，处理重叠和跨日。
- 事件：高低心率、步行稳定性事件等，不能画成普通连续折线。
- 训练：`HKWorkout` 摘要与关联统计。
- 相关样本：血压等需要保持组合关系。
- 特殊对象：心电图、听力图、用药、临床记录采用独立适配器，不能塞进普通数量样本协议。

Apple 官方说明 `HKStatistics` 默认会先合并多来源再计算；若指定 `separateBySource` 才由 App 自己合并。[HKStatistics 多来源行为](https://developer.apple.com/documentation/healthkit/hkstatistics)

## 6. 推荐实施顺序

扩展不挤占当前 P0 闭环，按以下顺序实施：

1. 完成 S07 个人基线和趋势引擎，确保新增指标有统一质量门禁。
2. 建立指标注册表与五种基础查询策略，不改变当前核心页面结果。
3. 第一扩展批：步行与跑步距离、爬楼层数、步行速度、步长和 VO₂ max 已完成；训练摘要与步行平均心率继续作为后续候选。
4. 第二扩展批：身体测量、行动能力、正念和日照。
5. 建立“全部健康数据”分类列表、搜索、置顶和分组授权入口。
6. 对血氧、血压、血糖、听力、营养、症状和生殖健康逐组做需求与安全评审；通过后才实现。
7. 临床记录、用药、路线和原始心电保持冻结，直到满足 L3 的重新评估条件。

每批只实现一个权限组，并完成：映射、查询、空状态、来源处理、单位、覆盖率、详情、趋势资格、测试、真机验证和日志，再开始下一组。

## 7. S04-12 验收结论

- 已确认“全部数据”作为长期覆盖目标，不解释为一次性请求所有权限。
- 已形成 L0～L3 数据目录和接入边界。
- 已确定今日页使用核心/置顶卡片，全部数据使用独立分类入口，洞察集中承载趋势和分析。
- 已确定分组、按需、只读授权流程。
- 已记录临床记录、用药、路线和原始心电的冻结条件。
- 本任务没有修改真实 HealthKit 权限，也没有读取或记录新的真实数据。
